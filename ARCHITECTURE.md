# Shila Architecture (Proposed)

## Status and scope

This is a planning document based on `idea.txt`, not a description of deployed software. Shila is a Persian-first, chat-style personal assistant whose first use case is personal expense tracking, particularly daily purchases. The long-term vision includes other personal-assistance capabilities, but their scope is not yet defined. Next.js is the selected framework for the primary PWA, with a single Cloudflare-deployed web application as the preferred direction. Cloudflare Agents memory, Cloudflare D1, and Google authentication remain the stated platform directions; their integration and the exact deployment topology still need validation.

The initial flow should let a signed-in user describe a payment or purchase in natural language, resolve ambiguity, confirm the extracted details, store the transaction, and review their own spending. No transfer of money is implied by recording a payment.

## Conceptual components

1. **Next.js PWA:** Browser-accessible, installable where supported, with Persian-first, RTL-friendly chat and transaction review and server-side entry points for authenticated application logic. Users can type or dictate into the same editable text field where browser/device speech input is available; Shila replies in writing. The client displays proposed records and asks for confirmation or corrections; it does not directly write to the ledger. Offline operation is not assumed.
2. **Authentication boundary:** Google sign-in establishes an application user identity. Server-side authorization uses that identity for every conversation and ledger operation; the client cannot choose another user's ID.
3. **Assistant orchestration:** Server-side logic behind the Next.js application manages the conversation, calls an LLM for interpretation or responses, requests clarification, and routes explicit user actions to application services. Initially, this can be straightforward application logic rather than a separate autonomous agent. LLM output is untrusted input.
4. **Conversation memory:** Cloudflare Agents memory retains the conversation and contextual information needed for continuity, subject to retention and deletion policies. Memory is not the authoritative transaction store.
5. **Transaction service and ledger:** Application logic validates amounts, units, dates, ownership, confirmed user intent, and any known purchase items before writing financial records to Cloudflare D1. D1 is the source of truth for financial history and later spending summaries; purchase items need not have individual paid prices.

Conceptual path: `User -> chat client -> authenticated assistant service -> extraction/clarification -> confirmation -> validated transaction service -> D1`. Conversation context is maintained separately through Cloudflare Agents memory. Reports read the authorized user's D1 records, not a model's recollection.

## Speech input boundary

The day-one contract is **text in, written response out**. Speaking may be the user's preferred way to populate the editable input via Chrome or the device keyboard, but that speech service's availability, Persian recognition quality, network behavior, and handling of audio are platform-dependent. Keep typing as the guaranteed fallback, show dictated text for correction before submission, and send the resulting text through the same expense clarification and confirmation flow. Do not require Shila to collect audio or request microphone access for the first release; test `fa-IR` dictation on target devices and networks before treating it as a dependable input path. Uploaded voice messages, an app-controlled microphone, spoken replies, and real-time voice need separate product and privacy decisions later.

## Web and deployment decision

Use Next.js for the PWA and its server-side entry points, aiming to deploy the web application together on Cloudflare rather than requiring separate frontend and API applications. The first expense flow must work without a native installation. This selects a framework and a one-web-application goal, not a particular Next.js rendering mode, adapter, or guarantee of a single Worker. Before implementation, verify the Cloudflare deployment path for PWA installability, Google sign-in, streamed chat responses, Agents memory access, and D1 bindings; supporting Cloudflare resources may still be needed. Keep authentication, orchestration, and transaction validation as clear logical boundaries even when they run in one application.

## Later device and SMS access

The PWA cannot monitor a device's incoming SMS. Bank-SMS reconciliation is not part of the first release. Later, a user may explicitly share or paste a bank message for interpretation; whether an OS share target is supported remains to be decided. Optional automatic SMS receipt would require a separate Android APK, distributed from Shila's website for users who choose the feature. The APK would present the hosted PWA in a WebView so web UI deployments can update without an APK release, while a small native component receives opted-in bank messages and sends filtered candidate events directly to the authenticated backend. Native code, permissions, and the APK itself still require signed releases and an update path; no specific wrapper framework is selected.

Keep raw SMS out of the WebView/native bridge where possible. The Android component must request explicit permission, filter unrelated messages on-device, securely link to the user's account, handle offline delivery and duplicates, and allow unlinking or revocation. A bank SMS is neither proof of a settled payment nor a complete purchase record: reconcile it with existing drafts and ask the user to confirm before a D1 write. Do not assume this Android-only access works on iOS. Browser camera or location access, if later required, needs separate user-initiated permission and purpose-specific handling.

## Future capability routing

Keep a boundary between conversation orchestration and domain capabilities. The first capability is expense recording; future personal-assistance domains may warrant specialist agents or services with explicit input/output contracts. A possible later path is `chat -> orchestrator -> selected specialist -> authorized application service`. This is an extensibility direction, not a requirement to implement agent-to-agent delegation in the first release.

- The orchestrator may select a capability, but neither it nor a specialist gains direct authority to read another user's data, write financial records, access device data, or initiate payments. Application services enforce authentication, permissions, validation, and any required user confirmation.
- Limit each capability's available tools and data to its task. Preserve enough redacted tracing to understand routing and failures without logging sensitive conversation or financial content.
- Cloudflare Agents memory is the planned conversation/context facility, not by itself a decision to use a multi-agent framework. Evaluate a framework only when multiple real domains need multi-step delegation or long-running work, against Cloudflare compatibility, cross-platform data flow, authorization, observability, latency, and cost. No AWS or other agent framework is selected.

## Transaction lifecycle

1. Receive a user message such as a payment to a person or a daily purchase. An LLM may propose structured fields and identify missing or uncertain information.
2. Resolve ambiguity before saving: amount and currency/unit (including what `KT` means), payment versus purchase, date/time, and counterparty or merchant when known. For purchases, invite item descriptions and quantities; ask only for details that matter to the user's record or a comparison. Do not require per-item prices or invent missing information. Preserve the original wording as provenance only if retention is justified.
3. Present the proposed record to the user and require a clear confirmation. Corrections return to the draft; unconfirmed drafts are not ledger transactions.
4. Validate again on the server and create a user-owned D1 record. Use a request or confirmation identifier to prevent duplicate entries on retries. Provide a way to correct or reverse mistakes while retaining an audit trail.
5. Read records for summaries with clear units, date ranges, and provenance. Do not present model-derived estimates as posted transactions.

## Data and trust boundaries

- **Identity:** Verify Google sign-in server-side and map it to a stable application user ID. Apply ownership checks to memory and D1 access, not just to UI routes.
- **Financial data:** Store canonical numeric values with explicit currency/unit and timestamps; do not silently convert Persian numerals, colloquial abbreviations, or local calendar dates without validation. Define precision, timezone, and calendar behavior before implementation.
- **Purchase evidence:** Distinguish the confirmed basket total and item facts from actual item prices, calculated prices, and external reference estimates. Check that known line totals and adjustments do not contradict the payment; keep any unexplained remainder unknown rather than forcing item prices to sum to the total.
- **Model calls:** Treat prompts, extracted fields, and generated answers as fallible. Limit exposure of personal data to external providers, validate structured output, and prevent tool calls from bypassing confirmation or authorization.
- **Privacy:** Use least-privilege access, secret management, encryption in transit, appropriate retention and deletion policies, and redacted operational logs. Obtain separate consent for media or SMS ingestion. Bank messages and photos may contain unrelated sensitive information.
- **Insights:** Spending warnings and price comparisons must distinguish personal history from broader samples, note sample size and time/location where relevant, and avoid unsupported claims about inflation or a "bad purchase." A basket-total comparison cannot identify the overpriced line item when actual item prices are unknown.

## Purchase and pricing boundaries

Plan a D1 purchase record linked to its confirmed financial transaction, with zero or more item entries; non-purchase payments need no items. Preserve user-supplied descriptions and quantities, optional product identity or package details, and optional **actual** unit/line prices with their source. Unknown line prices remain unknown. Keep discounts, fees, tax, and unitemized remainder distinguishable where applicable so a known breakdown can be checked against the paid total. A future product catalog identifies comparable goods; a separate dated price-observation history records evidence, rather than one mutable price per product. Neither a complete catalog nor price matching is a prerequisite for initial purchase capture. No concrete schema or normalization rules are selected yet.

For a later high-priority pricing capability, authorized price editors may add product descriptions, photos, and dated price observations with evidence type, source, currency/unit, region, and review/correction state. A package image may identify a product but does not verify its selling price. A confirmed private single-item purchase may also yield a **derived historical per-unit reference** if product identity, quantity, paid total, and discounts/fees allow a defensible calculation. Retain its date, currency/unit, region when known, and derivation provenance; it is not a direct line-price report. Editor access must be scoped to catalog/observations, never to private transaction data. Define moderation, duplicate handling, stale-price policies, and product matching before treating this data as reliable.

With explicit user opt-in, eligible user-derived observations can contribute to reference ranges for other users in the same coarse region. The path is `private purchase -> validated eligible observation -> privacy-checked regional aggregate -> reference comparison`, not access to the originating ledger record. Do not publish individual observations, identities, exact location or time, or small groups that could identify a buyer; require sufficient independent, recent comparable contributions, and mark editor versus user-derived sources in the displayed evidence. Corrections, reversals, and consent withdrawal must invalidate affected contributions and refresh aggregates under an explicit retention policy. A manually specified region can support comparison without requiring device location permission; never silently use precise location.

Compare the confirmed **basket total** against an appropriately matched range of recent reference observations when individual paid prices are unavailable. Match quantity, brand/variant, package size, unit, region, time, and currency; withhold a warning on weak evidence and disclose the baseline and uncertainty. A user's older single-item reference may inform the comparison, but cannot fill in the actual price of that item in a later multi-item basket or establish the other items' prices by subtraction. Reference prices are not invoice lines and must not be written into actual paid-price fields; any displayed per-unit value calculated from a paid total must be labeled as derived rather than user-reported.

Later, pilot explicitly uploaded product photos with an existing vision model as optional suggestions for the same text-first purchase draft. A photo containing several goods is not equivalent to a labeled close-up: a whole-image similarity score cannot reliably identify each product, and hidden items or nearly identical packages should remain uncertain. Start by using the user's item descriptions to guide suggestions and allow "unknown" matches; text/image conflicts require user resolution rather than silent replacement. Evaluate representative Persian-language, multi-item photos for exact-product accuracy, appropriate abstention, correction effort, latency, and cost before adding per-item localization/crops, catalog-image retrieval, or custom model training. No vision model is selected.

Treat receipt photos or digital invoices as a separate experiment: they may contain actual line prices, but extraction still needs user review. Limit and protect uploads, define retention and model-data exposure, and require confirmation before saving any extracted facts. The initial text flow and stored purchase items must not depend on image processing.

## Phased capabilities

- **Initial focus:** Editable text chat with written replies and optional browser/device dictation into the text field, Google sign-in, clarification and confirmation of expenses, invitations to describe purchased items without requiring their individual prices, D1 purchase detail and transaction history, and basic per-user spending review.
- **High-priority next capability (timing open):** Moderated product/reference-price observations, basket-level comparison and qualified warnings, plus optional photo and separate receipt pilots. Expand image recognition only if evaluation shows enough benefit to justify its cost and complexity. These require evidence quality, privacy, provenance, consent, and failure-handling decisions before release.
- **Later exploration:** Other personal-assistance domains and, if justified, specialist agents; purpose-limited location access, uploaded voice-message transcription or an app-controlled microphone, contextual price questions, historical price trends, and user-shared or optional Android-received bank-SMS reconciliation. Each requires its own permissions, applicable consent, provenance, validation, and failure-handling design.
- **Future possibilities:** Real-time voice and in-app payments. Payment initiation needs separate compliance, security, and provider decisions and must not be conflated with expense recording.

## Decisions to resolve before implementation

- Amount conventions: supported currencies/units, the meaning of `KT`, decimal precision, and exchange or conversion policy.
- Locale conventions: Persian digit handling, calendar input/display, transaction timezone, and mixed Persian/English messages.
- Speech input: test Persian dictation on target Chrome/keyboard combinations and networks, including transcription mistakes in amounts and units; do not assume a browser speech API, provider, or audio-processing policy is available everywhere.
- Record semantics: required transaction fields, purchase item descriptions/units, partial and unitemized baskets, adjustments and actual-price provenance, corrections/reversals, deduplication, and whether income or transfers are in scope.
- Pricing: editor verification and evidence, product identity and matching, rules for deriving historical observations from single-item purchases, consent and withdrawal, safe regional granularity and contributor thresholds, reference freshness and confidence thresholds, and which release includes warnings or image/receipt assistance; set image pilot success criteria before choosing detection, retrieval, or fine-tuning.
- Platform specifics: Next.js deployment adapter and runtime compatibility on Cloudflare, streamed responses, Agents memory APIs, D1 bindings/schema and migration workflow, LLM provider, Google auth flow, and attachment storage if media is added.
- Optional Android path: supported SMS formats and matching rules, APK signing and distribution, WebView/authentication isolation, permission handling, secure device-to-account linking, event delivery, and native updates.
- Orchestration: which future domains justify specialist capabilities, when delegation is beneficial, and whether any agent framework is compatible with the chosen runtime and trust boundaries.
- Data governance: retention and deletion for conversations and financial records, external model data processing, consent for future SMS/media use, and how price observations can be aggregated without exposing individual users.
